## Summary by area (H-005)

1. **Gamepad support (`auxForever/gamepad.lua`, `docs/gamepad.md`):** Safe with mouse and keyboard. When `InputUtil.IsGamepadUIEnabled()` is false (`[Code]`), `frame:HookScript('OnShow')` returns at line 774 before creating `hints` or `dialog` or setting any override bindings; `hints` has no `OnUpdate` until created (and hides when aux closes); and `aux.show_popup` / `aux.hide_popup` pass straight through to `StaticPopup_Show` / `StaticPopup_Hide`. It never writes to `GamepadMode`, `SmartNavigation`, `FrameControlsManager`, or `UIParent` (`[Code]`). Two gamepad-mode edge cases in `show_popup` and `find_popup` are noted in Finding 4.
2. **The price API promise (`auxForever/core/api.lua`, `docs/api.md`):** Pricing random-ending gear by `price_key` does **not** break the 0.7 API contract. `docs/api.md:36-38` has documented since 0.7 that a link keeps its random ending (`"of the Eagle"`), which aux prices apart, while a numeric ID means the plain item. However, 0.7 saved all gear under `item_id .. ':0'`, so `AuxForeverAPI.GetLatestPrice(itemID)` and `GetUsualPrice(itemID)` (and plain base links) can return stale 0.7 prices for random-ending gear unless `:0` is cleared when a suffixed key is recorded (Finding 7).
3. **Price keys from names (`auxForever/util/info.lua`):** `split_ending` handles `" of the "` items (`Band of the Steadfast Hero`, `Redemption of the Mage`) and plain items cleanly when the base item's name is known. One gap remains when `GetItemInfo(item_id)` has not cached the base item yet (Finding 1).
4. **One row per price (`auxForever/gui/auction_listing.lua`):** All 7 findings and note 8 from `docs/reviews/2026-11-08-one-row-per-price.md` are fixed and tested in commit `4ce16cc`. Sorting by the `For sale` or `Seller` column header and preserving selection when the first bucket of a merged row is bought still use single-bucket fields (Finding 5).
5. **The Post tab and gear (`auxForever/tabs/post/core.lua`):** Matching by item name, `other_endings_lowest`, `skip_key`, and clearing `other_endings_lowest` on `update_item` work as intended. One issue in `refresh_entries`: `on_abort` sets `listings_ready[item_key] = true`, which unlocks `Post` on incomplete listings if a gear scan is interrupted (Finding 2).
6. **Waylaid Crates (`auxForever/tabs/search/crate.lua`):** The scan, partial-bundle calculation, and tooltip caching are clean and avoid per-frame work. One guard is missing in `crate_bundles_from_text` to ensure only Waylaid Crate tooltips match `- <count> <name>` lines (Finding 6).
7. **Saved prices across versions (`auxForever/core/history.lua`, `auxForever/core/scan.lua`):** Full scans (`history.collect` and `finish_collect`) and completed searches (`scan_item_keys` with `state.views`) aggregate units across every version of an item before computing the 5% market price. However, `scan_item_keys` calls `record_view` after each version (`page`) rather than after all versions finish, so a search stopped mid-item overwrites today's market price with a partial view (Finding 3).
8. **The tests (`tests/slow_server.lua`, `tests/timing_test.lua`, `tests/load_test.lua`):** All tests pass in both themes (`load_test.lua` and `timing_test.lua`). Every 0.8 feature has coverage; adding regression tests for Findings 1 to 7 will close the remaining gaps.
9. **The release text (`docs/changelog.md`, `docs/curseforge-description.md`):** `docs/changelog.md` has a contradiction on whether the Sniper tab merges rows, and `docs/curseforge-description.md` states an `[Unknown]` belief (E6, newest listing at a price sells first) as plain fact and is missing the 0.8 features other than gamepad (Finding 8).

## Findings (ordered most serious first)

### 1. `info.price_key` returns `item_id .. ':0'` when the base item's name is not cached yet, causing `item_key_price_key` to misclassify uncached gear versions as `:0`

- **Where:** `auxForever/util/info.lua:521-548` (`M.price_key` and `M.item_key_price_key`), `auxForever/tabs/sniper/core.lua:248-252` (`check_list`), `auxForever/tabs/post/core.lua:957-969` (`skip_key`), `auxForever/util/info.lua:296` (`M.browse_record`).
- **What:** In `M.price_key(item_id, name)`:
  ```lua
  local base = base_names[item_id]
  if not base then
      base = GetItemInfo(item_id) or (item_info(item_id) or empty).name
      if base then
          base_names[item_id] = base
      end
  end
  if base then
      local ending = split_ending(name, base)
      if ending then
          return item_id .. ':' .. strlower(ending)
      end
  end
  return item_id .. ':0'
  ```
  When `C_AuctionHouse.GetItemKeyInfo(key)` (`[Code]`, `[Seen]`) has returned `key_info.itemName` (such as `"Medicine Staff of Arcane Protection"`), `GetItemInfo(item_id)` for the base item (`4575`) may still return `nil` if the client has not seen the base item in the session and `aux.account_data.items[4575]` is empty. Because `base` is `nil`, `price_key(4575, "Medicine Staff of Arcane Protection")` falls through to line 537 and returns `"4575:0"` instead of `"4575:of arcane protection"` or `nil`.
- **Why it matters:**
  1. `M.item_key_price_key(key)` (`info.lua:542-548`) is documented to return `"its price_key once the client knows the version's name, nil while it is still loading"`, and `post/core.lua:957-969` (`skip_key`) and `sniper/core.lua:248-252` (`check_list`) rely on `nil` when the key cannot be resolved yet. Instead, when `key.itemSuffix ~= 0` and `GetItemKeyInfo(key)` has loaded `itemName` while `GetItemInfo(key.itemID)` has not loaded the base name, `item_key_price_key(key)` returns `"4575:0"`.
  2. In `sniper/core.lua:248-252`, the Sniper looks up `item_facts("4575:0", 4575)` for `"Medicine Staff of Arcane Protection"`, finds no usual price under `:0`, and skips the deal without calling `need_check`.
  3. In `browse_record` (`info.lua:296`), fast-mode search rows get `record.price_key = "4575:0"` until the base item is cached.
  - **Fix:** If `base` is `nil` in `price_key(item_id, name)`, either fall back to splitting on the first `' of '` (`strmatch(name, '^.+( of .+)$')`) when `base` is unknown, or in `item_key_price_key(key)` return `nil` when `(key.itemSuffix or 0) ~= 0` and `not base_names[key.itemID]` and `not GetItemInfo(key.itemID)` and `not (item_info(key.itemID) or empty).name`. Falling back to `strmatch(name, '^.+( of .+)$')` when `not base` (without caching `base_names[item_id]`) handles almost every random-ending item in Forever (`[Seen]`) even before `GetItemInfo(item_id)` is cached.
- **How sure:** High (`[Code]`, verified in `info.lua:521-548`, `sniper/core.lua:248-252`, and `post/core.lua:957-969`).

### 2. `on_abort` in the Post tab's `refresh_entries` sets `listings_ready[item_key] = true`, unlocking `Post` and auto-pricing from incomplete gear listings when a scan is interrupted

- **Where:** `auxForever/tabs/post/core.lua:583-584` (`M.disabled_reason`), `auxForever/tabs/post/core.lua:945-952, 983-988` (`refresh_entries`).
- **What:** On the Post tab, `disabled_reason()` (line 583) keeps `Post` faded with `"Reading the listings..."` while `auto_price_key == selected_item.key and not listings_ready[selected_item.key]`. For a single-key item (`by_key == true`), `on_page_scanned` (line 946) sets `listings_ready[item_key] = true` and `auto_pick_price()` right before calling `scan.abort()`. For gear (`by_key == false`), `on_page_scanned` does not abort because all versions of the item must be scanned before the price is known (`on_complete`, line 993). However, `on_abort` (lines 983-988) unconditionally sets `listings_ready[item_key] = true` and calls `auto_pick_price()`:
  ```lua
  on_abort = function()
      buyout_records[item_key] = existing_records[item_key] or {}
      listings_ready[item_key] = true
      auto_pick_price()
      refresh = true
      scan_id = 0
  end,
  ```
- **Why it matters:** If a gear scan on the Post tab is aborted before all versions are read while the player stays on that item (for example, clicking `Full scan` in the top bar, which calls `scan.start` and aborts the previous scan, or if the scan times out), `on_abort` marks `listings_ready[item_key] = true`, runs `auto_pick_price()` on partial or empty records (picking a higher listing or `other_endings_lowest` / `history.value` as if the cheaper versions did not exist), and enables the `Post` button. Removing `listings_ready[item_key] = true` and `auto_pick_price()` from `on_abort` (since `on_page_scanned` already runs both before the intentional `scan.abort()` on line 949) ensures `listings_ready` is only set when the scan actually finishes reading the item.
- **How sure:** High (`[Code]`, verified in `tabs/post/core.lua:583-584, 945-998`).

### 3. `scan_item_keys` calls `record_view` after each version (`page`) rather than after all versions finish, so a search stopped mid-item overwrites today's market price with a partial view

- **Where:** `auxForever/core/scan.lua:513-532` (`scan_item_keys`), `auxForever/core/history.lua:226-248` (`record_view_of`).
- **What:** In `scan_item_keys`, `state.views` accumulates records across versions (`page = first_page, last_page`) so that when an item has multiple versions on the auction house (`[Seen]`, such as three versions of `Medicine Staff of the Owl`), the 5% market price and unit count are computed across all versions together. However, `record_view(records, complete)` is called inside the `for page = first_page, last_page` loop after each individual version (`scan.lua:525`).
- **Why it matters:** Suppose an item has 3 versions on the auction house (version 1 has 1 expensive listing at 5g; versions 2 and 3 have 10 listings at 1g), and the player already recorded a full view earlier today (from a Full scan or previous search: `market = 1g, units = 11`). If the player starts a full search and stops it (or starts another search) after version 1 finishes but before version 2 is read, `record_view` has already run for version 1 with `complete = true`, overwriting today's `record.market` (`5g`) and `record.units` (`1`) in `history` with just version 1's view. Calling `record_view` once after the `for page = first_page, last_page` loop finishes (iterating over the accumulated `state.views` when `not state.stopped`) guarantees that `history.record_view` only records a price when all versions of that browse row have been read.
- **How sure:** High (`[Code]`, verified in `core/scan.lua:513-532` and `core/history.lua:226-248`).

### 4. Gamepad `show_popup` leaves `dialog.editBox` with keyboard focus while gamepad focus is on `Cancel`, and `find_popup` can pick an earlier `DIALOG`-strata menu over `dialog`

- **Where:** `auxForever/gamepad.lua:123-135` (`find_popup` and `root`), `auxForever/gamepad.lua:452-456, 513-516` (`create_dialog` and `show_popup`), `auxForever/tabs/search/saved.lua:31-35` (`AUX_RENAME_FAVORITE`).
- **What:**
  1. **EditBox focus mismatch in `AUX_RENAME_FAVORITE`:** In `show_popup(name, data)` (`gamepad.lua:513-516`):
     ```lua
     if def.OnShow then def.OnShow(dialog, data) end
     set_focus(two and dialog.button2 or dialog.button1)
     ```
     For `AUX_RENAME_FAVORITE` (`saved.lua:34`), `def.OnShow` calls `self.editBox:SetFocus()`. Immediately after, line 515 calls `set_focus(dialog.button2)`. Because `focused` was not `dialog.editBox`, `set_focus` (`gamepad.lua:54-69`) does not call `dialog.editBox:ClearFocus()`. That leaves `focused = dialog.button2` (`Cancel`) while `dialog.editBox:HasFocus()` is `true`:
     - `hint_labels()` (`gamepad.lua:656`) checks `is_type(focused, 'EditBox') and focused:HasFocus()`, which is false because `focused` is `dialog.button2`, so the hint strip shows `A: Select / B: Close` instead of `A: Done typing / B: Stop typing`.
     - Pressing `B` (`back()`, `gamepad.lua:399`) checks `if is_type(focused, 'EditBox') and focused:HasFocus()`, which is false, so `B` closes the whole rename popup instead of stopping typing.
     - Pressing `A` activates `focused` (`Cancel`), dismissing the dialog even if the player just typed a new name.
     - **Fix:** In `show_popup`, call `set_focus(two and dialog.button2 or dialog.button1)` *before* `if def.OnShow then def.OnShow(dialog, data) end`, and then `if def.hasEditBox and dialog.editBox:HasFocus() then set_focus(dialog.editBox) end`.
  2. **`find_popup` order when another `DIALOG`-strata frame is open:** `Settings` (`frame.lua:370`), the quick search menu (`tabs/search/quick.lua:237`), and the Filter Builder menu (`tabs/search/builder.lua:68`) all have frame strata `'DIALOG'` and are created at load time, whereas `dialog` (`gamepad.lua:438`) is created lazily as a later child of `frame`. Because `find_popup` (`gamepad.lua:123-130`) returns the first visible `'DIALOG'` child in `frame:GetChildren()` order, if `dialog` opens while one of those menus is open (for instance, `AUX_SCAN_ALERT` or `AUX_SEARCH_TABLE_FULL`), `root()` returns the menu instead of `dialog`, trapping D-pad navigation behind the modal dialog.
     - **Fix:** In `root()` (`gamepad.lua:132-135`), check `if dialog and dialog:IsShown() then return dialog end` before `find_popup(frame)`.
- **How sure:** High (`[Code]`, verified in `gamepad.lua:54-69, 123-135, 399-419, 513-516, 656` and `tabs/search/saved.lua:31-35`).

### 5. Sorting merged rows by the `For sale` or `Seller` column header uses single-bucket fields, and buying the first bucket of a merged row can shift row selection when scrolled

- **Where:** `auxForever/gui/auction_listing.lua:193-195` (`quantity_column` `cmp`), `auxForever/gui/auction_listing.lua:238-248` (`Seller` `cmp`), `auxForever/gui/auction_listing.lua:1039-1046` (`SetDatabase`).
- **What:**
  1. **`For sale` sort (`auction_listing.lua:193-195`):** `quantity_column.cmp` compares `record_a.count * (record_a.auction_count or 1)` with `record_b.count * (record_b.auction_count or 1)`. On a merged gear row (`record.group_count = 56`, while the first bucket's `record.auction_count = 2`), clicking the `For sale` column header sorts that row as `2` instead of `56`. Using `record_a.count * (record_a.group_count or record_a.auction_count or 1)` sorts by the displayed count.
  2. **`Seller` sort (`auction_listing.lua:238-248`):** A merged row with multiple sellers displays `"4 sellers"` (`record.group_sellers = 4`), matching the dimmed multi-seller look of commodity rows (`not record.owner`), but `record.owner` is still the first bucket's seller name (`'Kadathi'`). Clicking the `Seller` column header sorts `"4 sellers"` under `'K'` instead of treating `(record.group_sellers or 1) > 1` like a multi-seller row (or sorting by seller count).
  3. **Row selection after buying the first bucket of a merged row (`auction_listing.lua:1039-1046`):** When the player buys the first auction in a merged price row, `RemoveAuctionRecord` removes `prev_selected` (that first bucket) from `self.records`. In `SetDatabase`:
     ```lua
     if not self.selected and prev_selected then
         for _, record in pairs(self.records or empty) do
             if record == prev_selected then
                 self.selected = record
                 break
             end
         end
     end
     ```
     Because `prev_selected` is no longer in `self.records`, `self.selected` falls back to `self.rows[prevSelectedIndex].record` (line 1049). That works when the table is at the top (`headIndex == 0`), because `prevSelectedIndex` is a visual row index (`1..#self.rows`), not an offset into `self.rowInfo.rowMap`. If the player scrolled down (`headIndex > 0`) before buying from a merged row, `self.rows[prevSelectedIndex]` has not been updated yet for the new `rowMap` (or points to a different row if an earlier row vanished). Adding a second pass `if not self.selected and prev_selected and prev_selected.price_group then` that matches `record.price_group == prev_selected.price_group` keeps `self.selected` on the remaining auctions of that same merged price row regardless of scroll position.
- **How sure:** High (`[Code]`, verified in `gui/auction_listing.lua:193-195, 238-248, 1039-1052`).

### 6. `crate_bundles_from_text` matches any tooltip line starting with `- <number> <text>`, even on non-crate items

- **Where:** `auxForever/tabs/search/crate.lua:27-40` (`M.crate_bundles_from_text`).
- **What:** `crate_bundles_from_text(lines)` checks every line of every hovered item's tooltip for `^%s*%-%s*(%d+)%s+(.-)%s*$` without checking whether the tooltip belongs to a Waylaid Crate (`"Fill the crate"` or `"following list:"`, `[Seen]` in `docs/forever-auction-house.md` section 10).
- **Why it matters:** If any non-crate item in Forever has a tooltip line starting with a hyphen and a number (for example, a negative resistance or stat line formatted with a space, or flavor/quest text with a dashed list), `crate_bundles(item_id)` permanently caches that `item_id` in `bundle_cache` as a Waylaid Crate, appends `"Cheapest way to fill it"` to its tooltip, and makes `Alt-click` search the auction house for the matched text instead of the item. Checking that at least one line in `lines` contains `'Fill the crate'` (case-insensitive) before returning `bundles` costs one `strfind` and prevents false matches.
- **How sure:** Medium-High (`[Code]`, defensive guard against non-crate tooltips).

### 7. `AuxForeverAPI.GetLatestPrice(itemID)` and `GetUsualPrice(itemID)` (and base gear links) can return stale 0.7 `:0` prices for random-ending gear

- **Where:** `auxForever/core/api.lua:18-28`, `auxForever/core/history.lua:150-167, 226-248`, `docs/changelog.md:82-84`.
- **What:** `docs/changelog.md:82-83` states: *"Prices aux saw for gear before this update were kept under one price per item and are no longer used for gear."* For random-ending gear seen in game (which has an ending like `"of the Owl"`), 0.8 looks up `4575:of the owl`, so the old `4575:0` entry is ignored. However, `4575:0` remains in `aux.faction_data.history`.
- **Why it matters:**
  1. If another addon calls `AuxForeverAPI.GetLatestPrice(4575)` or `GetUsualPrice(4575)` by numeric item ID, `key_from(4575)` returns `"4575:0"`, which returns the stale 0.7 mixed-ending price forever (dimmed after 7 days in `history.value`, but never expiring in `history.latest` or `AuxForeverAPI`).
  2. If a player clicks or hovers a base `[Medicine Staff]` link in chat or a database addon (or runs `/aux price Medicine Staff`), `link_price_key` returns `"4575:0"` and shows the old 0.7 mixed price.
  - **Fix:** Whenever `history.process_auction` or `history.record_view_of` (or `finish_collect`) writes a price for a suffixed key (`strmatch(key, '^(%d+):(.+)$')` where the suffix is not `'0'`), delete `data[item_id .. ':0']` (and `value_cache[item_id .. ':0']`) if present. That retires the 0.7 mixed `:0` entry for any item that actually has random endings, while keeping `:0` intact for gear that never has random endings (like `[Blackvenom Blade]`).
- **How sure:** High (`[Code]`, verified in `core/api.lua:18-28` and `core/history.lua:150-248`).
